# Workq

Distributed job queue scheduler. 

# Description

Workq can coordinate n "workers" to complete generic jobs from a queue of tasks. 
The exact task can be generic - in the initial test case, a simple image transformation is the task, 
but multiple kinds of tasks can be configured, stored in the queue, and carried out by the same set of workers. 

# Components

Workq consists of three types of components:

**Producer** - Generates jobs (currently: image transformations) and 
enqueues them to Redis. Each job is a JSON document containing task type, 
input/output paths, and task-specific parameters. One producer is needed for each task specified. 

**Redis Queue** - Central job queue. Workers atomically claim jobs to 
prevent duplicate processing.

**Workers** - Stateless containers that claim jobs from the queue, execute 
the task, and write results to shared storage. Multiple workers can run 
concurrently. and can carry out multiple kingds of tasks by importing modules from the /tasks subdirectory. This contains the python scripts to be executed by the worker(s), which are specified to each job by the config file, currently the image transformation job: 

from PIL import Image

def process_image(job):
    img = Image.open(job["input_path"])
    img = img.resize((256, 256))
    img = img.convert("L")
    img.save(job["output_path"])

# How to use

The primary user interface is managed via a volume on the host which is mounted to both the producer and worker containers. The volume contains three subdirectories: 

**/config** - Contains the .json config, currently: 
{
            "input_path": "<absolute path to directory>",
            "output_path": "<absolute path to directory>",
            "task_name": "transform",
            "enqueued_at": ""
        }
This encodes the information needed by the worker to complete the task, and is the actual structure which is shipped to the Redis Queue

**/input** - This directory contains the input files to be worked on (currently input images). If there are multiple jsons in the /config folder specifying different tasks, then there must be multiple specified subdirectories created to associate with the input_path object specified in the config json.

**/output** - This directory contains the output files which have been generated by the worker (currently, output images). Again, if there are multiple jsons in the /config folder specifying different tasks, then there must be multiple specified subdirectories created to associate with the output_path object specified in the config json.

To run, Use: 

docker compose up --build 

information logs will output to the terminal with status, and hopefully your output files will now appear in the output folder. The worker will, upon job completion move the input file to a completed folder /input/completed, where it will be stored until it either ages out or the directory becomes too big. This process is itself managed and checked by the worker each time it completes a job. The system will idle if the input folder(s) are emptied, and any files transferred to that location will immediately be initiated into the queue by the associated producer. 

To stop the system, use: 

docker compose down

# Data Flow Description

**1** The producer container initializes a python script on start, which checks the /config folder and imports the .json file, builds the job, and sends it to the Redis Queue. 

**2** The Redis Queue holds the job key/values imported from the producer. 

**3** Workers claim a job according to the dwell time in the queue (FIFO), and process tasks according to the jobs imported from the queue. worker outputs to /output, and moves the original file from /input to /input/completed.
